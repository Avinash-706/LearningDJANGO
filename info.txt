========================
DJANGO NOTES
 ========================

 
 1. DJANGO TEMPLATES
 ------------------------
 -> Django templates are used to store `.html`, `.css`, and `.js` files for rendering dynamic web pages
 -> Templates separate PRESENTATION (UI) from BUSINESS LOGIC (Python backend)
 -> Templates are rendered by Django views using the `render()` function
 -> Example:
       from django.shortcuts import render
 
       def home(request):
           return render(request, "index.html")
 
 -> Advantages:
    ✓ Clean separation of logic & design
    ✓ Easy integration with static files (CSS/JS)
    ✓ Powerful templating engine with filters, tags, loops
 
 
 
 2. CONTEXT IN DJANGO
 ------------------------
 -> Context = Dictionary that passes dynamic data from backend (views.py) to frontend (template)
 -> Example:
       def home(request):
           peoples = ["Avinash", "Rohit", "Sneha"]
           return render(request, "index.html", {"peoples": peoples})
 
 -> In `index.html`:
       <ul>
         {% for person in peoples %}
           <li>{{ person }}</li>
         {% endfor %}
       </ul>
 
 -> Uses:
    ✓ Dynamic rendering of data
    ✓ Easy communication between Python code & HTML
 
 
 
 3. DJANGO TEMPLATE LANGUAGE (DTL) BASICS
 ------------------------
 -> `{{ variable }}` → Displays variables passed in context
 -> `{% tag %}` → Used for logic/conditions/loops
 -> Example:
       {{ peoples }}                  # Prints the list
       {% for person in peoples %}    # Loop through list
          {{ person }}
       {% endfor %}
 
 -> **For Loop Special Variables**:
    * `forloop.counter` → 1-based index of current iteration
    * `forloop.counter0` → 0-based index
    * `forloop.first` → True if first iteration
    * `forloop.last` → True if last iteration
    * `forloop.revcounter` → Countdown from last to first
    * Example:
          {% for person in peoples %}
             {{ forloop.counter }} : {{ person }}
          {% endfor %}
 
 
 
 4. DJANGO TEMPLATE FILTERS
 ------------------------
 -> Filters are used inside `{{ }}` to modify data before rendering
 -> Syntax: `{{ variable|filtername:parameter }}`
 -> Example:
       {{ text|truncatechars:80 }}
       -> Cuts text after 80 characters
 
 -> Common & Prominent Filters:
    * `truncatechars:n` → Cuts string after n characters
    * `truncatewords:n` → Cuts string after n words
    * `length` → Returns length of list/string
    * `lower` / `upper` → Converts to lowercase / uppercase
    * `title` → Converts to Title Case
    * `date:"D M Y"` → Formats a datetime object
    * `default:"value"` → If variable is empty, use default
    * `join:", "` → Joins list items with given separator
    * `safe` → Marks content as safe HTML (removes auto-escaping) [⚠ risky]
 
 -> Example:
       {{ "avinash dhanuka"|title }}
       -> Output: "Avinash Dhanuka"
 
       {{ mylist|join:" - " }}
       -> Output: "a - b - c"
 
 -> **Why Filters?**
    ✓ Make data user-friendly
    ✓ Avoid writing formatting logic in views
    ✓ Keep templates cleaner and readable
 

 
 5. DRY CONCEPT (DON'T REPEAT YOURSELF)  
 -----------------------------------
 -> Purpose: Remove redundancy in code (avoid writing the same HTML/CSS/JS multiple times).  
 -> Common use: Header, Footer, <html>, <head>, <script> tags repeated in multiple pages.  
 
 SOLUTION: BASE TEMPLATE INHERITANCE
 -> Create a base.html file containing the common structure. Example:
    <html>
    <head>
        <title>Django App</title>
    </head>
    <body>
        {% block start %}
        {% endblock %}
    </body>
    </html>
 
 -> In other templates, extend it:
    {% extends "base.html" %}
    {% block start %}
        <h1>Page Content Here</h1>
    {% endblock %}
 
 WORKING OF EXTENDS:
 -> {% extends "base.html" %} tells Django template engine to first load base.html.  
 -> Then it replaces only the {% block %} sections with the child template’s content.  
 -> Advantage: Code reusability, easier maintenance, faster development.  
 


 6. WHAT IS MODELS IN DJANGO?  
 -----------------------------------
 -> A Model is a Python class that represents a database table.  
 -> Each attribute of the class represents a field (column) in the table.  
 -> Example:
    class Student(models.Model):
        name = models.CharField(max_length=100)
        age  = models.IntegerField()
 
 -> In "models.Model", the "Model" is a BASE CLASS provided by Django ORM.  
 -> Django ORM = Object Relational Mapper → maps Python objects to database records.  
 


 7. WHICH FIELD IS AUTOMATICALLY ADDED?  
 -----------------------------------
 -> Django automatically adds:  
    id = models.AutoField(primary_key=True)  
 -> Purpose: Unique identifier for each record (like objectId in MongoDB).  
 -> Works as Primary Key in SQL (by default if no custom PK is defined).  
 
 

 8. WHAT IS MIGRATION IN DJANGO?  
 -----------------------------------
 -> After creating/changing a model, you must apply migrations.  
 -> Migration = Way to propagate model changes into the database.  
 
 WORKING:  
 -> makemigrations: Creates migration files (like version history of DB schema).  
 -> migrate: Applies these changes into the actual database (SQLite/MySQL/Postgres).  
 -> Relation with SQL:  
    - Model class → Python representation  
    - Migration → SQL script generated from Model  
    - Database → Final applied structure  
 


 9. DJANGO MIGRATION COMMANDS  
 -----------------------------------
 -> python manage.py makemigrations  
    - Detects changes in models.py  
    - Creates new migration files inside "migrations" folder  
 
 -> python manage.py migrate  
    - Applies migrations to database  
    - Actually creates/updates SQL tables  
 


 10. HOW DJANGO COMPARES CHANGES IN MIGRATIONS  
 -----------------------------------
 -> Django runs all previous migrations in order  
 -> Creates a STATE of the database schema  
 -> Compares the state with the current models.py  
 -> If differences found → generates new migrations  
 -> If no differences → "No changes detected"  
 
 DIFFERENCE BETWEEN makemigrations vs migrate:
 -> makemigrations → Prepares the migration file (does not touch DB)  
 -> migrate → Executes the migration file (applies to DB)  
 


 11. INTERVIEW QUESTION: WHAT IF WE DELETE MIGRATION FILE?  
 -----------------------------------
 CASE 1: If a migration file is deleted but DB already updated →  
 -> Django compares current migrations with db.sqlite schema  
 -> Error: "Inconsistent migration history"  
 
 CASE 2: If db.sqlite record is deleted but migration exists →  
 -> Django will try to reapply → may cause errors or duplicate tables  
 
 CAN DJANGO FIX IT AUTOMATICALLY?  
 -> NO, manual fixing required.  
 -> Options:  
    - Recreate migration file  
    - Use python manage.py migrate --fake to skip  
    - Drop database and reset migrations (not recommended in production)  



12. DJANGO SHELL (python manage.py shell)
----------------------------------------
-> Django provides an interactive Python shell integrated with your project
-> It loads all models, settings, and configurations automatically
-> Helps to test and interact with database objects using ORM (Object Relational Mapping)

EXAMPLE:
    stu = Student(name="Avinash", age="22", email="avunash@gmail.com", address="HCL Road")
    stu.save()   -> Saves the student object into database

Shortcut method:
    Student.objects.create(name="Sahil", age="17", email="sahil@gmail.com", address="MP")

Fetching records:
    Student.objects.all()   -> Returns all Student objects as QuerySet
    Student.objects.all()[0].name     -> Access first student's name
    Student.objects.all()[0].address  -> Access first student's address

✅ USE CASE: 
   -> Used to quickly test model queries and perform CRUD operations without writing views/templates



 13. DJANGO ORM OBJECT CREATION
 ----------------------------------------
 METHOD 1 (Direct creation with save):
     stu = Student(name="Avinash", age="22", email="avunash@gmail.com", address="HCL Road")
     stu.save()
 
 METHOD 2 (Using create()):
     stu = Student.objects.create(name="Avinash", age="22", email="avunash@gmail.com", address="HCL Road")
 
 DIFFERENCE:
     -> METHOD 1:
         - Creates an object in Python memory only
         - Requires calling stu.save() explicitly to push it into database
     -> METHOD 2:
         - Directly creates and saves object into database
         - No need for .save() explicitly
 
 IMPORTANT:
     -> objects is called a **Model Manager**
     -> Model Manager is a gateway for database queries (objects.all(), objects.filter(), objects.create(), etc.)
 
 
 
 14. ERROR WHEN RUNNING DJANGO CODE OUTSIDE SHELL
 ------------------------------------------------
 -> If we try to run a normal Python file (.py) with Django-specific code (like importing models or ORM operations), 
    we get errors (ImproperlyConfigured, no settings configured)
 -> This happens because Django requires its settings and environment to be loaded
 
 SOLUTION:
     -> Run files using Django shell:
         python manage.py shell
     -> Or use "django-extensions" package to run custom scripts safely
 
 ✅ INTERVIEW INSIGHT:
     - Q: Why can't we run Django ORM code directly in normal Python shell?
     - A: Because Django needs settings.py (database config, installed apps, etc.) to be initialized.
          manage.py shell takes care of this initialization automatically.
